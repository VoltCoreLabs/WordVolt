# WordVolt — правила для Claude

Текстовый редактор уровня MS Word на чистом Rust + GPUI. Полный план: `plan.md`.

## Режим работы (экономия токенов)
- Отвечай по-русски, коротко: результат, затем 1–3 строки пояснений. Без пересказа диффа.
- Не перечитывай файлы, которые только что правил. Читай диапазоны (offset/limit), не целые файлы.
- Поиск — Grep/Glob, не `cat`/`find`. Крупный обзор кодовой базы — через Explore-агента.
- Не запускай `cargo build` целиком ради проверки: `cargo check -p <crate>`; тесты — `cargo test -p <crate> <имя>`.
- Выводы cargo фильтруй: `cargo check --message-format=short 2>&1 | tail -30`.
- Не создавай лишних файлов, README, комментариев-«воды». Не рефакторь вне задачи.
- Неясность по архитектуре — один конкретный вопрос с рекомендацией, не опрос.

## Ведение записей (память проекта)
- `plan.md` — единственный источник правды по задачам. После каждой завершённой задачи: поставь `[x]`, добавь дату.
- `docs/decisions.md` — ADR: одна запись = решение + почему (3–5 строк). Пиши при смене стека/архитектуры.
- `docs/log.md` — журнал сессий: дата, что сделано, что дальше (≤5 строк). Обнови в конце сессии.
- Неочевидные грабли (баги GPUI, версии, платформенные нюансы) — в раздел «Gotchas» ниже.
- В начале сессии читай только: этот файл + раздел «Текущий этап» в `plan.md` + последнюю запись `docs/log.md`.

## Стек (зафиксирован, менять только через ADR)
Rust 2024, GPUI (+ gpui-component), cosmic-text, ropey/собственная модель документа, quick-xml + zip (docx), printpdf/собственный PDF-экспорт, serde, thiserror, tracing. Подробности — `plan.md §2`.

## Архитектура (workspace)
- `wv-core` — модель документа, операции, undo/redo. **Без зависимости от GPUI.**
- `wv-layout` — вёрстка: переносы, страницы, колонтитулы (cosmic-text).
- `wv-io` — импорт/экспорт: .wvd (нативный), .docx, .md, .txt, PDF.
- `wv-ui` — GPUI: окно, ribbon, canvas страниц, диалоги.
- `wordvolt` (bin) — точка входа.
Правило: зависимости только вниз (ui → layout → core; io → core). Логику не писать в `wv-ui`.

## Документация — ничего не терять
- Любое решение (стек, библиотека, дизайн, процесс) → запись в `docs/decisions.md` (D-NNN) в том же коммите.
- Любая сессия → запись в `docs/log.md`. Новые папки/файлы → `docs/structure.md`. Дизайн-токены/компоненты → `docs/design.md`.
- Не дублируй содержимое между файлами — ссылайся (`см. D-009`).

## Живая пересборка (dev-loop, см. D-009)
- Разработка идёт через `cargo dev` (cargo-watch): сохранил файл → приложение пересобралось и перезапустилось само.
- Токены темы читаются из файла в dev-режиме и применяются на лету без пересборки.
- После правки UI-кода не запускай `cargo run` вручную, если dev-loop уже работает; смотри его вывод.
- Держи dev-сборку быстрой: не добавляй тяжёлые зависимости/build.rs без причины.

## Структура файлов (подробно: `docs/structure.md`)
- **Большие файлы всегда делим на маленькие.** Файл `.rs` ≤ 300 строк (без тестов), функция ≤ 50. Увидел файл больше лимита (даже чужой) — сначала отдельным коммитом разбей на модули, потом правь. Не дописывай в разросшийся файл.
- `mod.rs` только `pub mod`/`pub use`. Один файл = одна ответственность; новая фича = новый файл.
- У каждого крейта `README.md` (5–10 строк: назначение, API, чего нет) — читай его вместо кода.
- Перед созданием файла сверяйся с деревом в `docs/structure.md`; новые папки добавляй туда же.

## Дизайн (подробно: `docs/design.md`)
- **Блочная система:** общий светлый фон окна, на нём блоки (карточки/панели) и залитые кнопки с обводкой. Всё собирается из готовых компонентов блоков, не из разрозненных `div`.
- Сейчас **только белая/светлая тема**, но цвета, радиусы, отступы, обводки — только через токены `wv-ui/src/theme/` (никаких `rgb(0x...)` в виджетах), чтобы позже добавить тёмную тему заменой набора токенов.
- Приоритет: удобство и практичность (крупные цели клика, понятные состояния hover/active/disabled/focus), затем красота.
- Любой новый UI-элемент — через общие компоненты из `wv-ui/src/ui_kit/` (Block, Button, IconButton, Toggle, Dropdown…). Нужного нет — сначала добавь компонент туда.

## Код
- Edition 2024, `cargo fmt` + `cargo clippy -- -D warnings` перед коммитом.
- Ошибки: `thiserror` в библиотеках, `anyhow` только в bin. Никаких `unwrap()` вне тестов.
- Любое изменение документа — через `Command` (для undo/redo), не прямой мутацией.
- Индексы текста — байтовые в UTF-8 на границах графем (`unicode-segmentation`); кириллица/эмодзи обязательны в тестах.
- Тесты для core/layout/io обязательны; UI тестами не покрываем, только ручная проверка.

## Git-воркфлоу (на каждую задачу от пользователя — полный цикл, без доп. разрешений)
1. **Ветка:** от актуального `main` создать `feat/<тема>` (`fix/`, `docs/`, `refactor/`, `chore/` по типу). Одна задача = одна ветка. Никогда не работать прямо в `main`.
2. **Работа:** маленькие атомарные коммиты, сообщение короткое, императивом (`Add paragraph split command`). Конец сообщения — строка Co-Authored-By из системной подсказки.
3. **Проверка перед PR:** `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`. Всё зелёное, иначе чинить, а не пушить.
4. **PR:** `git push -u origin <ветка>`, затем `gh pr create` — заголовок коротко, описание: что сделано, как проверено, ссылка на пункт `plan.md`. В конец описания добавить пометку «🤖 Generated with Claude Code».
5. **Мерж при успехе:** если проверки (локальные и CI, `gh pr checks`) зелёные — `gh pr merge --squash --delete-branch`, затем `git checkout main && git pull`. Если красные — не мержить, починить или сообщить пользователю.
6. **Записи:** в `plan.md` отметить `[x]` + дату, дописать `docs/log.md` — это коммит в той же ветке до мержа.
7. **Нельзя без прямого указания пользователя:** force-push, `reset --hard`, правка истории `main`, мерж с красными проверками, пропуск хуков (`--no-verify`).
- Если нет remote или `gh` не авторизован — довести до коммитов в ветке и сказать пользователю, что осталось (PR/мерж).
- Итог задачи в чате — 2–3 строки: ветка, ссылка на PR, смержено или нет.

## Gotchas
- `gpui-kit 0.7.x` — API нужно сверять с docs.rs перед использованием (код в `src/main.rs` — набросок, может не компилироваться).
- Платформа разработки: Windows 11 (GPUI на Windows использует DirectX; нужен Visual Studio Build Tools).
